# ⚠️ 模拟盘账本两处数据完整性问题（Cursor 独立确认）

> 由 WB 在复核"生产入场时点"时发现，Cursor 在服务器独立复验，**两条均证实**。

## 问题 1：`buy_price` 不是成交价（模拟盘收益被高估）

### 证据（Cursor 独立复验，51 条 top2 记录）
- **13/51（25.5%）的 `buy_price` 落在当日 [low, high] 之外** → **不可能是任何成交价**。
- **16/51（31.4%）恰好等于 D−2 收盘价**。
- 铁证：`2026-08-05` 归档 `603893` `buy_price = 184.04`，而当日区间 **187.00–204.30**；184.04 正是 **08-03 收盘**。
- **`data/paper_trading.json` `trade_log` 直接拿它记账**：`"2026-08-05 09:36","603893",买入,"price":184.04` → **账本层面高估收益**。

### 方向与量级
被污染记录**系统性 < 当日最低价**（这些是跳空高开的动量票，D−2 收盘 < D 区间）→ **买入价记低 → 收益被高估**。
WB 抽样：某笔记 **+11.7%，真实约 +8%**（单笔高估 ~2pp 量级）。

### 时间窗（按日分布）
| 期间 | 状态 |
|---|---|
| 07-27 ~ 07-30 | 正常 |
| **08-03 ~ 08-21** | **间歇性坏**（08-05/08-10/08-12/08-17 全坏；其余 1/2 坏） |
| **08-25 起** | **全部正常** |

→ **bug 窗口 ≈ 2026-08-03 → 08-21**，08-25 后已自愈/修复。

### 根因（WB 定位，Cursor 01:30 采信）——**不是公式错，是上游 K 线缓存不新鲜**
**`buy_price` 的定义就是「选股时那份 K 线缓存的最后一根收盘」，从来不是成交价。**
- 链路：`top2.json` ← `morning_live_fund_select.py:904` 的 `buy_price or price`；
- `buy_price = kline_df.iloc[-1]["close"]`（`vm25_scorer.py` / `ml_screener_v12.py`）；
- ⇒ **缓存滞后 k 天，`buy_price` 就等于 D−k 收盘**。

**两个窗口必须分开记**（同为"缓存不新鲜"的不同表现）：
| 窗口 | 表现 | 解释 |
|---|---|---|
| 08-03 ~ 08-18 | **16/18 精确 = D−2 收盘** | `sync_kline_root.py` 原文：「2026-08-04 起东财接口被风控，每轮仅成功 10-20 只 → 根目录文件覆盖崩坏」；crontab：「`[DISABLED 2026-08-10 东财源被风控…] update_kline_cache.py`」→ 缓存滞后 2 天 |
| **08-25 起** | **不落在任何近期收盘** | `buy_price` 变成 `None` 后 **fallback 到实时价** → **不是"修好了"，是换了个错法**（看似正常，实则记的是下单瞬间价而非成交价） |

⇒ **修复方向不在 `buy_price` 公式，而在 K 线缓存新鲜度**（东财风控是总病根，见 `2026-09-11-kline-0910-recovery.md`）。

## 问题 2：归档目录缺 5 个交易日 —— **根因已定位：不是"没跑"，是"跑了覆盖前一天"**

`output/daily_picks_archive/` 在 07-27→09-10 的 33 个交易日里**只有 30 个目录**，缺：
**2026-07-28、07-29、07-31、08-04、08-24**。

### 根因（Cursor 深挖，代码级）
`scripts/archive_daily_picks.py::_day()` **从源文件字段推归档日**：
```python
for p in (PICKS, REC, SCORE10):            # morning_live_picks.json / daily_recommend.json / score_top10.json
    for k in ("asof","trade_date","date","run_at","generated_at","scanned_at"):
        v = str(d.get(k) or "")
        if len(v) >= 10 and v[0].isdigit():
            return v[:10]                   # ← 归档日 = 源文件 asof，不是"今天"
```
→ **当源文件 `asof` 滞后时，归档不报错、不新建目录，而是把前一天的目录再写一遍。**

### 日志实证（`output/logs/daily_picks_archive.log`，35 条 `_meta` 配对）
| 归档运行日(`archived_at`) | 写入的 `day` | 后果 |
|---|---|---|
| 2026-07-28 / 07-29 / 07-30 | 都是 `2026-07-27` | **`2026-07-27/` 被连写 3 次** |
| 2026-07-31 | `2026-07-30` | 07-30 被覆盖 |
| 2026-08-04 | `2026-08-03` | 08-03 被覆盖 |
| 2026-08-24 | `2026-08-21` | 08-21 被覆盖 |

- 其余 29 次为同日归档（正常）。
- 另有 `2026-07-26`（**周日** 17:44 手工/一次性目录），非交易日。
- 因此 30 个目录 ≠ 33 个交易日；**唯一交易日归档 ≈ 29**，且 4 个目录被重复写过。

### 影响（比"缺失"更需警惕）
- 任何"逐归档目录"的研究：**日期数被高估**（如"290/300 笔 × 33 交易日"实际 ≤29 个信号日）；若滞后日的 picks 与前日相同，还会**重复计数**；
- **信号显著性进一步缩水**（板块 streak 的核心桶 n=33 本就小）；
- R6 sample B（"~30 天"）同样受影响；
- 现有研究**无需推翻结论**，但**n/日期数须重标**。

## 处置建议（待老板定）

1. **归档脚本修**：`_day()` 加兜底——若 `asof` 不是"今天或上一个交易日"，则用**当前交易日**作为目录名，并落 `data_alert`（不允许静默覆盖旧目录）。
2. **写入加不覆盖保护**：目标目录已存在且 `day` 相同 → 跳过并告警（防重复写）。
3. **补归档缺口**：4 个被覆盖的目录内容可能已非原日数据，**不建议回补**；在研究口径中显式标注"有效信号日 ≤29"。
4. **历史账本 `buy_price`**：不回改，分析中排除 08-03→08-21。
